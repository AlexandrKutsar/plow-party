# Match

The Match lifecycle inside a Session: WaitingForPlayers → Countdown → Playing → Results → next Match, who takes which Slot, the Match clock, and the placement table (GDD 3.1–3.3). Rules live in `Simulation/` as deterministic C#; the Host steps them once per Fusion tick. Specs: `.scratch/match/spec.md`, `.scratch/bots/spec.md` (WaitingForPlayers and seating).

## Entry points

- `MatchRules` — phase machine and clock, built from `MatchSettings`: `NextPhase(phase, phaseElapsed, restartRequested, allSlotsFilled)`, `PhaseRemaining`, `PlayingElapsed`, `PlayingRemaining`, static `IsInputLocked(phase)`, `StartsNextMatch(from, to)`, and `PhaseElapsed(tick, phaseStartTick, deltaTime)`; `WaitsForRestartRequest` when Results has no time limit. Holds no state.
- `WaitingRules` — who fills the Slots while waiting: `PlanSeats(hasMatchmakingResult, matchmakingResult, playersPresent, slotLimit)` → `SeatPlan` (Slot count, expected Players, planned Bots), `ScheduleBotArrivals(count, random)` (sorted times inside the arrival window), `BotsToSeat(plan, players, bots, waitingElapsed, arrivals)`, static `AllSlotsFilled` and `HasFreeSlot`. Holds no state.
- `MatchPlacementRules.Rank(slots, scores, count, output)` — fills `MatchPlacement`s (Slot, Score, Place) ordered by Score descending, ties by Slot; tied Scores share a place and skip the next (1, 2, 2, 4), like the backend. Allocation-free; returns the rows written.
- `IMatchClock` — read-only clock on every peer: `IsRunning`, `Phase`, `MatchNumber`, `PhaseRemaining`, `PlayingElapsed`, `PlayingRemaining`.
- `IMatchResults` — the recorded placement table (`PlacementCount`, `GetPlacement(index)`), `WaitsForHost` (Results has no time limit), and the Host's `RequestRestart` (`CanRequestRestart` is true only on the Host during Results).
- `MatchSettings` — durations, the Bot arrival window and the fallback Slot count, filled from `MatchConfig`.

## Rules worth knowing

- WaitingForPlayers (cap 15 s) → Countdown 3 s → Playing 180 s → Results 10 s → Countdown of the next Match. `ResultsDuration` 0 means Results waits for the Host's restart. A restart request only counts during Results.
- WaitingForPlayers ends the moment every Slot is taken (Players plus Bots), never on time alone: at the cap every free Slot gets a Bot at once, which fills them. The phase remaining time is the cap countdown Hud shows.
- Seat plan: on the Host, `MatchmakingResultStore.TryGet` gives the Players Meta matched (`ExpectedHumans`) and `MaxSlots`, both clamped to the Spawn Points. Without a Matchmaking Result (Match scene started directly, dev quick start) the Host expects the Players already connected (at least itself) in `FallbackSlotCount` (6) Slots. The plan reserves Slots for expected Players; Bots fill the rest gradually at random times inside `BotArrivalStart`–`BotArrivalEnd` (1–8 s), so the Arena fills up visibly. An unexpected extra Player takes a free Slot while there is one, which leaves one Bot fewer.
- The Slot list is fixed when Countdown starts (the backend Roster, ADR-0013). A Player who connects later is refused at the connection request; one who slips through the join is disconnected; both are logged. The refused client's start answers `SessionStartOutcome.Refused` and Meta shows "Матч уже начался" in the Menu (from Quick Play or a Room Code, and from `MatchSceneQuickStart`, which leaves to the Menu); a disconnected one is a lost Session, which `SessionExit` also routes to the Menu.
- "Play again": the Session keeps its Participants. Results → Countdown respawns every Vehicle in its Slot, and a Slot freed by a Player who left gets a Bot at once, so the next Match starts full without waiting again. A Player who leaves during a Match leaves the Slot empty until then.
- The networked state is the phase and the tick it started; every peer derives the clock from its own tick, so nothing is written per tick except the input lock. A client's tick is predicted ahead of the Host, so near a transition its clock can read a fraction of a second past the phase end until the new phase arrives; views clamp (Countdown never shows 0).
- Input is locked outside Playing (WaitingForPlayers included) through Vehicle's `IsImmobilised` Modifier, written by the Host every tick for every registered Vehicle. `MatchDriver` carries `[DefaultExecutionOrder(-100)]` so it runs before `VehicleWorldDriver` and the lock applies on the very tick Playing ends. Match is that Modifier's only owner until Freeze exists.
- Placements are recorded once, on entering Results, from DropOff's `IScoreReader`, so Score credited by a Delivery still unloading after the end does not change the table.
- A new Match respawns every Vehicle in its Slot (`VehicleSpawner.RespawnAll`): the fresh Vehicle starts at its Spawn Point with an empty Bucket and zero Score, so Match never resets Bucket or DropOff state itself.

## Network

- `MatchDriver` — scene `NetworkObject` (`Prefabs/MatchDriver.prefab`), implements both interfaces and Snow's `ISnowClock` (`IsPlaying`, `PlayingElapsed`, `MatchRestarted`); registered in `MatchScope` with `RegisterComponentInHierarchy` as `IMatchClock`, `IMatchResults`, `ISnowClock`, and itself. The Host plans the seats and enters WaitingForPlayers on spawn (Match number 1); every tick it lets `MatchSeating` seat arrivals and due Bots before stepping the phase. `MatchRestarted` is a host-side C# event raised after the respawn of a new Match; Snow resets its grid on it, since the Snow Grid outlives Vehicles.
- `MatchSeating` — host-side entry point in `MatchScope` (also registered as itself for `MatchDriver`). Owns which Slot holds whom: queues `PlayerJoined` arrivals and seats them on the next tick (Nickname from the `ParticipantToken` in the connection token via Participants' rules, fallback "Игрок N"; a random Critter; Account Id kept host-side), refuses `ConnectRequested` once closed or full, seats Bots (pool Nickname, random free Slot) through `ParticipantRoster.Seat` and `VehicleSpawner.Spawn` with no input authority, and vacates a leaving Player's Slot. Logs every seating decision under `[Match]`.
- `MatchConfig` — the ScriptableObject behind `MatchSettings`; asset `_Project/Configs/MatchConfig.asset`, registered in `RootLifetimeScope`.

## Depends on

Participants (`ParticipantRoster`, `ParticipantProfiles`, `ParticipantsConfig`), DropOff (`IScoreReader`), Snow (`ISnowClock`, implemented here), Vehicle (`VehicleRegistry`, `VehicleSpawner`, `NetworkVehicle`), Infrastructure (`NetworkRunnerEvents`, `MatchmakingResultStore`), Shared (`MatchmakingResult`, `ParticipantToken`), Fusion, VContainer. Hud and Bots depend on Match. Snow cannot reference Match (Match → DropOff → Snow), which is why the clock seam is Snow's interface. The assembly is in Fusion's `AssembliesToWeave`. Submitting the Match Result belongs to Meta. Decision: ADR-0018.
